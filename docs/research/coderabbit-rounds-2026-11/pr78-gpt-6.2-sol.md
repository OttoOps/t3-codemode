## 3. Runtime cost

- **GitHub.** At all heads an admitted pass makes zero requests for no tracked PRs, otherwise `ceil(PRs / 100)` aliased reads. A same-head, unqueued, mergeable wait adds a serial fresh read and usually one mutation. An OPEN/UNKNOWN fresh read can attempt three reads with two one-second sleeps. Those retries predate the PR. Queue/head mismatch and retryable reads add no immediate extra request in the final version. They defer some repairs or retries to the next pass. The expected-head mutation guard survives all rounds (`b366675` `src/reconcile.rs:198,211,511`, `src/merge.rs:14,22,85,178,198`).
- **SQLite.** An admitted pass in all three versions reads `pr_seen` in full three times, for queued tracking, the comparison map and pruning. It also does a keyed comparison per returned PR and normally a guarded upsert, even when only `at` changed. Terminal rows persist, so even an empty board eventually scans its history. The final prune still executes the SELECT when `stale` will filter everything. Round 3's targeted cadence query reduces Rust decoding on skipped timer passes, although SQL may scan JSON rows. Round 1 adds a wait lookup per merge attempt. The final head fixes it to a primary-key lookup (`2d7d2e7` `src/reconcile.rs:168,234,243`; `b366675` `src/reconcile.rs:182,207,231,282,304,330`, `src/store.rs:484,530`).
- **New local work.** A stored-message lookup for most handled cards on every pass replaces the original fallback lookup when the preview had no PR. That is justified for safety. A gate check may load the same message again for the head. Gate clearing adds a card scan plus link reads/writes. `tell` now reads the same link twice per notified ticket. Full-board and per-item error recovery cause extra retries and may leave a stored message without a usable card because `raise` inserts the message first (`2d7d2e7` `src/reconcile.rs:220`; `b366675` `src/reconcile.rs:268,289,391,483,665,689`).
- **Locks and wall time.** `reconcile_lock` spans the full pass, including GitHub awaits and delivery. Round 1 moves the cooldown check inside that lock. The broader workflow lock covers some board repairs and is held over T3 reads/sends on the terminal path, as in the original. `wf.merge` bypasses it, so these lock scopes still permit stale interleavings. For the watcher path, GitHub runs inline with the board pass. A timeout is per `gh` process, so multiple fresh reads or multiple waits can delay the watcher much longer than one timeout. Page load spawns the check and does not wait for it (`b366675` `src/reconcile.rs:198,389,454,536,552`, `src/wf.rs:793,839`, `src/github.rs:10,38`, `src/board.rs:1147`, `src/watcher.rs:16`, `src/web.rs:84`).
- **Verdict.** Healthy network cost stays essentially flat and the additional local work is small at this scale. Distinguishing retryable errors from final refusals justifies another scheduled pass. The avoidable cost is duplicated scans and network delivery under the workflow lock. The ADR records one GitHub point each for a 1-PR and 52-PR read. Its claim of no lock during GitHub I/O is only true of the broad workflow lock, and its 30-second watcher-delay and rate claims omit multi-call passes, page checks and earlier watcher work (`b366675` `docs/decisions/0001-github-reconcile-cadence.md:58,70`, `docs/src/board.md:200`). This review did not benchmark.

### Defects the final head still has

- **Moderate, plausible: an older removal cancels a newer approval.** This is a regression introduced by the late change that consumes a wait after a removal report. If the PR has an existing OPEN observation, then GitHub records a removal, and the user reapproves while blocked before the next check, the previous observation's removal timestamp differs. The final code checks age only when there is no prior observation. It raises a card for the old removal and discards the new wait. Round 2 can raise the same stale report but it leaves the new approval intact. The fresh `wf.merge` read already has the removal timestamp and omits it when it saves a wait (`b366675` `src/merge.rs:111,165`, `src/reconcile.rs:346,361`; `8ad3a16` `src/reconcile.rs:304`). Conversely, with no prior observation, a same-second removal after approval cannot pass the strict timestamp comparison. Retire only a wait that predates the removal with evidence from that approval's observation.
- **Moderate, narrow: suppressing duplicate gates also suppresses a queue mismatch.** The new boolean means some gate was replaced. It carries no ticket or approved-head identity. Any replaced gate can cause a wait for a different ticket to be retired. Even with one ticket, an open gate plus a wait at A and a PR already queued at B now yields only the replacement gate. The mismatch branch never runs. Both effects need one decision based on queue membership, gate identity and approval identity (`b366675` `src/reconcile.rs:356,361,504,521`).
- **Moderate, rare: a partial timeline loses the only tracking source.** For a callerless queued PR with no card or worker, an OPEN/unqueued result with null timeline writes `queued=false`. No later query reads that PR once the timeline recovers. Preserving `removed_at` prevents duplicate reports after a later null response but does not help the first exit observation. This is present in the original and final (`2d7d2e7` `src/reconcile.rs:234,276`; `b366675` `src/reconcile.rs:282,313,358`).
- **Moderate, rare but routine operations can trigger it: delivery and card replacement are not atomic.** If a first terminal observation has only a card or wait, a restart or store error after their removal but before the outbox insert can permanently lose the wake. If the event is already durable and the prior observation is OPEN, a restart before the observation write can duplicate it. A same-head background direct merge marks MERGED before enqueueing the event. A moved-head card is resolved before the replacement exists. The outbox handles ordinary downstream send failures once it has the entry (`2d7d2e7` `src/reconcile.rs:269,312,392`; `b366675` `src/reconcile.rs:334,390,426,493,563`, `src/merge.rs:205`, `src/wf.rs:793,863`).
- **Moderate, narrow: approval selection and observation state still race.** The reconciler selects A, then calls the public merge path, which looks up the current wait again. That can select and consume B. A same-second identical reapproval defeats full-row comparison. A delayed enqueue write can overwrite a stored merge. Reading queued recipients apart from comparison rows also permits inconsistent snapshots. Round 1 narrows several deletion windows but the data model still permits these interleavings (`2d7d2e7` `src/merge.rs:161`; `b366675` `src/merge.rs:78,129,185`, `src/reconcile.rs:156,205,282,535`, `src/store.rs:472`, `src/clock.rs:41`). An expected-head rejection **after** the fresh read still removes the wait and emits a generic report. GitHub rejects the stale mutation, so the defect is losing the reapproval path (`b366675` `src/merge.rs:178,182`, `src/reconcile.rs:576`).
- **Low at present, higher if multiple tickets per PR are supported.** The board can track a PR against multiple tickets, but direct merge marks the PR globally complete. Another ticket never gets its event. The gate check visits only the first eligible card. The PR says one ticket per PR is the design. That invariant is absent from the implementation and sits awkwardly with the documentation's promise to notify each ticket (`b366675` `src/merge.rs:205`, `src/reconcile.rs:411,472`, `docs/src/board.md:211`). First-seen terminal PRs tracked only by a worker also stay quiet. That rule avoids waking a ticket for historical PRs, but also misses a new worker PR that merges before its first GitHub poll (`src/reconcile.rs:411`).
- **Low, surviving input ambiguity.** The digit heuristic rejects real all-letter SHA prefixes and silently uses the first-observed head. It also finds a head in the entire message, including unrelated prose. The PR number range check applies to card/worker URL text only. The public `wf.merge` still accepts values above GraphQL Int range before it queries GitHub (`b366675` `src/reconcile.rs:37,55,483`, `src/merge.rs:65,90`). Structured card metadata removes the head ambiguity.

## 5. Review behavior

There is evidence of review-driven churn. A one-line parser change and one exact counterexample generated an entire round. The next patch sequence grew one public JSON refusal field at a time, as each possible result from calling GitHub a second time appeared in a finding. The board docs followed that list closely, including a watcher-delay guarantee the code does not establish. By the final head there were six scenarios just for remote state changing around the fresh merge read, yet two separate reads of local state still chose recipients and decided whether to notify. This is a patch-selection problem. The record cannot establish that the author cared more about approval than correctness, and many of the review-triggered tests are good.

The author pushed back repeatedly. In the round-1 replies they kept the SHA digit heuristic to avoid treating prose like “head defaced” as a SHA, kept the expected-head direct-merge fallback after a queue is disabled, and deferred unique wait IDs and transactional delivery. In rounds 2–4 they explicitly deferred cross-ticket delivery and per-card gate baselines, a delayed enqueue overwriting a merge, the split queued-recipient snapshot, and the callerless null-timeline case. CodeRabbit acknowledged the snapshot race as follow-up work. The author also used write ordering where the reviewer requested a transaction and detected a fresh closure via a new wait rather than adding `closedAt` to storage. Those were deliberate scope calls.

I would have pushed back harder on round cadence and on treating each observation as a separate public merge outcome. Keep the early fixes and batch the rest around invariants: a retryable answer preserves approval, one head-move decision matches one gate or wait, and a terminal observation persists a wake before consuming its trigger. “One ticket per PR” is a reasonable simplification for this operator. Enforce it or document who owns the notification. “The race is microseconds” is an incomplete argument when some competing operations include a GitHub request and the watcher and page can both run against public calls.

## 6. Resubmission

Use `8ad3a16` as the starting patch on the desired main base. Rewrite the following behavior in a few coherent changes. The review heads contain rewritten feature commits, so use the cited changes as references.

1. **Keep repairs retryable and independent.** Reuse `d9a26ef`'s per-PR error handling and queue-observation-before-wait-delete change. Keep the approval until a replacement card or report exists, and change the link gate only as part of that repair. Carry forward the missing-alias diagnostic and the stale-worker snapshot guard (`b366675` `src/reconcile.rs:220,248,713`).
2. **Give background advancement one internal outcome model.** Keep one canonical wait identity and distinguish retryable read/mutation failure, terminal PR, blocked at approved head, moved head, queued head mismatch and success. Borrow the behavior from `b366675` `src/merge.rs:96,123,140,147,191` and `src/reconcile.rs:521,543`. Keep GitHub's expected-head guard. A failed expected-head mutation should leave the wait for a fresh observation. Decide explicitly whether a saved queue approval can turn into a direct merge when repository settings change. The current docs say yes, while issue #56 describes this background path as queueing. Either policy still needs head binding.
3. **Make drop and gate decisions before consuming the wait.** Preserve unrelated gates and read the full action text for legacy cards. Prefer typed PR/head metadata for new gates. Keep the useful removal report and queued-head mismatch behavior, but compare removal identity or time against *every* saved approval, persist a queue exit until its timeline is usable, and match deduplication to the actual gate, ticket and approved head. Clear the link gate only when its corresponding merge card resolves. Keep tests for reapproval after a removal and an already-queued moved head with an open gate.
4. **Persist terminal effects with the local transition.** Use one PR observation and one local operation that records the transition, retires the selected wait, resolves or replaces the exact card, and inserts the durable outbox event. Use a stable local terminal-event key for the owning ticket. Let the existing outbox perform T3 I/O after commit. This addresses the original lost-wake and duplicate-registration windows. Remote delivery still follows the existing retry semantics.

For one service, serialize merge/queue operations per PR across the interactive and background paths. Use a short local transaction for committing board state, without the global workflow lock held over GitHub or T3 I/O. The reconciler can still read GitHub in a batch, but should apply the observations against one local snapshot and avoid using a response that predates a newer local operation. Persist a per-approval ID if a snapshot can outlive the approval it read. That is a smaller invariant than full-row equality plus remove/restore branches. The board can keep its current cadence and existing outbox.
