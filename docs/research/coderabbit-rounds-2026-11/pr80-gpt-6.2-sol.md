**Verdict.** The review improved the updater. Round one was the best pass: it protected local systemd settings, restored both files on a failed cutover, and bounded a CI test that could hang. The later passes fixed genuine atomic-swap and rollback failures, then spent more of their effort on uncommon configurations and incomplete safeguards. Resubmit from `b962714` with the targeted changes below. The highest-risk path, a failed managed restart followed by recovery, still lacks an end-to-end test.

The original had a readable sequence, a focused `Swap` type, and a thin board integration. Its weakness was the success path's ownership of recovery: it mutated a second file outside rollback and treated the default executable and a port as enough information to manage the service. Round one was net positive. `UnitPlan` makes overwrite policy explicit. Keeping the old unit next to the existing binary rollback logic makes the common failure intelligible. One process lock is a reasonable cost even for one operator. Its first key, the state directory, did not match the executable and its fixed staging paths (`b962714:src/upgrade.rs:331-346,449-455`).

The final code gains a better lock key and a Unix swap that matches the operation it claims to perform. Readability declines in the manager code. `run` combines download, verification, manager discovery, target checks, file mutation, restart, and rollback. Manager details then spread across discovery, status, executable lookup and restart. The macOS adapter reads an on-disk plist using string splits, while discovery inspects the loaded job. The Linux adapter parses `ExecStart` text, and all platforms can fall back to the conventional executable on lookup failure (`d8ae5c4:src/upgrade.rs:233-309,600-619`). This still lacks proof that the answering process is the one restarted. The current identity scheme is a canonical executable path, a port, and a version string. There are no revisions or new SQL tables, columns, or Store methods. The board's single in-memory version slot and shutdown signal were present in the original. The cache grew from version plus successful-check time to include attempted-check time and source. The lock file carries no transaction state (`d8ae5c4:src/release.rs:166-175`, `src/wf.rs:221`, `src/upgrade.rs:392-411` at that head).

The original CLI tests checked real observable failures: bad checksums, wrong reported versions and unknown releases. The original board test drives the notice, dismiss-until-next-version, and reload states (`d8ae5c4:tests/update.rs:145-215,239-249`, `tests/board.rs:3160-3197` at that head). The deadline and zero-exit checks make the SSE regression test stronger (`b962714:tests/cli.rs:108-129`, `d8ae5c4:tests/cli.rs:129-130`). The same-executable/different-state-directory test also asserts a meaningful CLI outcome. Its exact lock filename and the exact directory listing assertions couple it to the mechanism. The final suite checks `Swap` with byte files and unit replacement with a planning function. The CLI fixture only puts tar and gzip on PATH and tests file-only update. It cannot exercise manager discovery, changed-unit rollback, or a failed restart. The test file is Unix-only. The Windows release smoke test in main exercises the installer, which stops the task before replacing its executable. It provides no evidence that the updater's rename, cleanup and restart work while the updater itself is executing from that image (`d8ae5c4:tests/update.rs:1,107-128,160-178,218-236`, `src/upgrade.rs:724-756`, `deploy/install.ps1:202-218`, `.github/workflows/release.yml:448-474` at that head).

## 3. Cost per pass

- **Release HTTP.** Same in all heads: one non-followed `/latest` request for explicit `--check` or a default update. An explicit tag skips lookup. An install then makes two logical downloads, archive and sums, with redirects. The lookup never calls the GitHub REST API directly. `gh` may make separate API requests for signed-in users. The original auth status queried all known hosts, round one limits status to GitHub.com, and final uses the active token. Request counts inside attestation depend on `gh`. Unix atomic replacement adds a hard link, or one backup copy if linking fails. See `d8ae5c4:src/release.rs:120-163` and `src/upgrade.rs:132-148,473-489,527-580` at that head. [GitHub CLI auth status](https://cli.github.com/manual/gh_auth_status) [GitHub CLI auth token](https://cli.github.com/manual/gh_auth_token)
- **Cache and database.** A fresh interactive notice has one cache read and zero HTTP. A stale successful check goes from one cache write to two after round one. A failed check goes from zero writes to one, so ordinary repeated invocations avoid retrying an offline lookup within the interval. The service reads its startup cache and checks on the existing 12-hour schedule, with one cache write on success. Source matching adds a string comparison, but alternating mirror and stock sources evict each other from the single slot. No release-related SQL writes or schema changes. Each successful local health probe invokes the existing health handler, which reads at least the watcher last-pass metadata row. Rediscovering releases adds no such probes. See `b962714:src/release.rs:236-248`, `d8ae5c4:src/release.rs:217-228,245-262`, `src/main.rs:248-279`, `src/server.rs:98-100`, `src/app.rs:469-479`, and `src/store.rs:311-313` at that head.
- **Manager and polling.** A stock running Linux cutover goes from discovery, status and restart to those same three calls plus an `ExecStart` query in final. Unit replacement adds a reload when applicable, and restoring a changed unit adds another reload on rollback. Round one adds one invocation of the installed executable's `--version` under the lock. The one preflight health GET already existed. The restart still polls every 250 ms between calls, with a 2 s request timeout and a nominal 45 s window per cutover or rollback. Final macOS adds status, SIGTERM and status polling to its original single kickstart. Windows adds status and can poll after a failed stop. The test-only busy-file retry has zero production cost (`f2356e1:src/upgrade.rs:183-199,224-245,272-283,398-435`, `d8ae5c4:src/upgrade.rs:192-209,233-309,422-459,600-686`, `76ab036:tests/update.rs:66-85`).
- **Lock duration.** The original had no lock. `b962714` and final acquire a nonblocking file lock after release selection and before the on-disk version check. They hold it through downloads, extraction, manager checks, restart, health polling, rollback and cleanup. Two 300 s download deadlines alone can occupy it for almost ten minutes. The final 150 s timeout applies per `quiet` child, including status probes inside a nominally 30 s stop loop. It does not cap the transaction or bound tar and `--version` children. The extra common-case process calls are cheap compared with the restart. Keeping serialization across mutation and recovery is justified. Download and validate in private scratch first, then lock, recheck the target, and do shared work. See `b962714:src/upgrade.rs:440-469`, `d8ae5c4:src/upgrade.rs:11-12,103-125,161-189,424-432,557-586`.

**Original defects that survived.**

- **High consequence, low trigger likelihood.** `--no-restart` deletes the known-good executable backup before the new binary ever serves, as does any update of a stopped service. If manual activation fails, there is no automatic route back. A subsequent file-only update can repeat that loss. Final's version check catches a later managed update only while the old process is still alive and answering. The recommended manual restart can take down the only healthy instance. See `f2356e1:src/upgrade.rs:416-428` and `d8ae5c4:src/upgrade.rs:620-657`. Staging followed by updater interruption also has no crash recovery. Unix atomic rename protects the executable path, but an interrupted unit+binary switch can leave a mismatched pair and `Swap::install` removes the old backup at the start of the next swap (`d8ae5c4:src/upgrade.rs:473-489,634-646`).
- **Medium, uncommon configuration.** Health checks prove a JSON version at a port. They do not validate HTTP success, process identity, or that the service accepts work. Original and final both use the same check for rollback. Final's incumbent-version guard does reject the reviewer's exact false-success example when a second instance already returns the target version at preflight, since the target differs from the incumbent. It still cannot authenticate the listener or establish that a successful response comes from a fresh managed process. See `f2356e1:src/upgrade.rs:183-199` and `d8ae5c4:src/upgrade.rs:192-209,620-631,664-686`.
- **Low, deterministic if the flags are combined.** `update --check --version` accepts the supplied tag and returns before any lookup, even if the tag never existed. The command can label the supplied tag “latest release.” Reject the combination or give it explicit semantics and test it (`f2356e1:src/upgrade.rs:333-354`, `d8ae5c4:src/main.rs:408-416`, `src/upgrade.rs:527-547` at that head).
- **Provenance error classification.** All heads interpret a failed auth command as unsigned mode. Final narrows the usual cause, but timeout, permission failure and missing auth still converge on “skipped.” Given the optional-attestation spec, confirmed absence can skip. An indeterminate probe needs its own error. The same ambiguity is present in manager detection. In final, a timed-out Linux status probe becomes false, so an actually active service can go through the stopped branch and lose its backup without health verification (`f2356e1:src/upgrade.rs:115-139`, `d8ae5c4:src/upgrade.rs:116-145,233-255,615-657`). A client timeout alone also cannot establish whether a systemd job it submitted has finished. [systemctl job behavior](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html)

The agent should have challenged three things sooner: the macOS change to an explicit issue behavior, the demand for a universal timeout without typed failure handling, and the suggestion that refusing one subsequent update preserves the last known-good binary. CodeRabbit issued three change requests and the final head went unreviewed. There is no recorded approval. Most of the added code addressed valid failure modes.

## 6. Resubmission

**Use `b962714` as the patch base.** Keep its SSE shutdown work, checks, notices, local-unit protection and coordinated rollback. The useful later hunks are inside rewritten feature commits, so port these behaviors directly.

1. **Use the Unix atomic swap from `76ab036` and the executable-scoped lock from `d8ae5c4`.** Keep the on-disk version recheck after the lock. Own a single backup across any unverified install. Preserve it on file-only and stopped-service updates. Refuse to overwrite a pending backup until the operator verifies the installed version or restores the previous one.
2. **Add a small manager preflight and a tested restart/rollback per supported platform.** Port the Windows recovery when the task has already exited and the configured executable guard from `daadc5b`. Resolve the loaded or registered executable using manager-appropriate queries. A failed query should produce an error for managed cutover. Distinguish absent, stopped, active and query failed. Give operations explicit deadlines. For macOS, either keep the issue's kickstart behavior and correct the docs, or make graceful stop an explicit acceptance criterion with a native test.
3. **Port active-account provenance and cache source matching from `8ebcd71`.** Separate an unavailable or signed-out `gh` from an unexpected probe error. Keep the custom Cargo-directory guard from `daadc5b` if developers use that layout. The small SSE exit-status and fixture-portability fixes can come with the affected tests.

Keep Linux unit refresh conservative as the spec requires. Install only a recognized stock replacement, write it atomically, and restore the prior bytes before starting the old executable. A divergent unit can be reported for operator review. One owned install path, one lock, one rollback candidate, and explicit handling of failed activation are enough for a single managed service. A release-process alternative is to have the installer own all service definitions, which requires changing the issue's Linux refresh requirement.

## 7. What to verify

The next quality gate should be an observable managed failure. Start A, stage B whose `--version` works but whose service exits on start, and assert that the same manager serves A with its prior unit, the command exits nonzero, and local edits survive. Cover the file-only path separately by verifying that A's bytes remain recoverable until activation of B. Exercise the Windows install and rollback on Windows before claiming support. These tests would have caught the most consequential review findings with less review churn. The rest of the board and cache tests are worth retaining.
